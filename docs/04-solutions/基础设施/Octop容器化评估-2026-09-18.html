结论 能容器化

能，而且官方已做好
多阶段 Dockerfile + 3 套 compose + 入口自动初始化 + HEALTHCHECK 齐全，官方镜像已发布到 GHCR。这不是社区凑的 Dockerfile。
但它面向家用/小团队
官方容器化目标是"一台机器、一个人管"，不是医院生产环境。直接照抄会踩 5 个坑，其中 2 个是等保/安全评审必问项。
不能水平扩展
单进程架构 + 进程内调度 + IM 长连接 + 本地文件 workspace。K8s 里只能 replicas: 1，扩容只能纵向。
官方镜像只支持 amd64

附带一个上游 P0 缺陷

一句话：容器化本身没有技术障碍，Octop 是"为自托管而生"的项目，Docker 是一等公民。真正的风险不在"能不能装进容器"，而在PG 模式崩溃循环、单副本约束、容器内 root 运行、ARM 缺位、离线交付这几件事——除 ARM 外都可在 1–3 人日内补齐，不是架构死结。

上游 P0 缺陷：PostgreSQL 模式下容器崩溃循环 本次发现

结论先行：官方 compose 明确宣传可以切 PostgreSQL（OCTOP_DATABASE_DRIVER=postgresql / OCTOP_DATABASE_URL），但照着配下去，容器只能启动一次，之后每次重启都会失败退出并被反复拉起。上游 issue 中无相关记录。

触发链条（源码逐行核对）

# docker/docker-entrypoint.sh:23
DB_FILE="${OCTOP_HOME}/octop.db"
# docker/docker-entrypoint.sh:47 —— 唯一判据是「SQLite 文件不存在」
if [ ! -f "$DB_FILE" ]; then
    ...
    if ! octop init --yes --admin-username ... ; then
        DEFAULT_PASSWORD="$(octop_random_password)"
        octop init --yes --admin-username ...   ← 没有 if 保护
    fi
fi
  1. PostgreSQL 模式下永远不会生成 octop.db。src/octop/infra/db/factory.py 的 open_database() 在 PG 分支直接 return PostgresPool(...)，不落任何 SQLite 文件；docker-entrypoint.sh 里 octop.db 只在这一处被引用。
  2. 于是 [ ! -f "$DB_FILE" ] 永远为真，每次容器启动都会执行 octop init。
  3. src/octop/cli/commands/init.py 开头就检查 ~/.octop 是否为空，非空即 raise SystemExit(1)：
    error: ~/.octop already exists and is not empty. Use --force to reset.
  4. 入口脚本把这次失败误判为"密码太弱"，换随机密码重试一次；第二次失败没有被 if 保护，配合 set -euo pipefail 直接终止脚本，容器退出。
  5. restart: unless-stopped 反复拉起 → 崩溃循环，且每次都会用新随机密码重写 credential.txt。
为什么这个坑特别毒：首次启动一切正常（目录为空，init 成功，能登录、能用），验收时看不出问题。第一次断电、升级、迁移之后就再也起不来——正好落在医院项目的运维期。

五个缺口 必须补

1. 容器内以 root 运行 安全评审必问

Dockerfile 全文没有 USER 指令，容器以 uid 0 启动。后果有两层：

  • 宿主绑定的 ~/.octop 目录会被 root 改写所有权，宿主普通用户后续读写、备份、迁移都会碰到权限问题；
  • Agent 具备 shell 执行能力，在容器内即 root 权限，配合挂载的宿主目录，等于把宿主对应路径的写权限交出去。

代价：修这条很便宜（加 useradd + USER + 宿主 chown），但不修在等保/渗透测试环节会被直接记问题项。

2. Playwright Chromium 未预装 功能缺位

Dockerfile 只通过 uv sync --extra browser 装了 playwright 的 Python 包，没有执行 playwright install chromium。官方 FnOS 文档也明写"Playwright Chromium 不预装，需要远程浏览器时在控制台按需安装"。

后果：镜像内置的浏览器自动化能力（harness-browser）在容器里开箱即用会失败，且安装脚本（scripts/install.sh）里的 Chromium 下载逻辑对容器路径不生效。同时 PLAYWRIGHT_BROWSERS_PATH 被写死在 /root/.cache/ms-playwright，一旦改非 root 运行，这个路径不可读，必须一起改。

3. 不能水平扩展（多副本） 架构约束

约束点多副本时的后果
进程内 APScheduler定时任务在多副本上重复触发
进程内唯一 HarnessProcessorWeb/IM/cron 状态不共享，请求落到不同副本行为不一致
IM 长连接（飞书/钉钉/QQ/Discord/企微）多副本争抢同一 bot 连接，消息随机丢或重复
Agent workspace 是本地文件系统不同副本看到的 workspace 不同，记忆/技能错乱
SQLite 默认单写者即使换 PG，上面三条依然存在
结论：只能 1 副本 + 纵向扩容。K8s 部署必须设 replicas: 1、更新策略 Recreate（不能 RollingUpdate，否则双实例重叠写）、PVC ReadWriteOnce。这也意味着没有高可用——单点故障只能靠重启恢复（好在设计上重启可从控制面库重建状态）。

4. 官方镜像只有 amd64 信创/鲲鹏场景

CI 里 platforms: linux/amd64 写死。鲲鹏、Apple Silicon、部分信创服务器都是 arm64，拉不到官方镜像，必须自行构建。已实测依赖树在 aarch64 上的可行性：

依赖类别实测结果结论
纯 Python 包188 个（占 78%）任意架构可用
C 扩展包41 个已有 aarch64 预编译 wheel（cryptography / psycopg-binary / pillow / pydantic-core / onnxruntime / pymupdf 等）直接装
无 aarch64 wheel11 个，其中 5 个是 pyobjc-*（macOS 专用，Linux 不装）；其余 5 个（oss2 / esdk-obs-python / aliyun-python-sdk-core / antlr4-python3-runtime / crcmod）为纯 Python sdist，uv sync 直接从源码装；evdev 是 C 扩展但只属于 desktop extra，容器不装无阻塞
Playwright Chromium官方 CDN 上确认存在 chromium-linux-arm64.zip（pinned 版本 1.61.0 对应 rev 1228，实测 196 MB 可下载）；更早的 rev 1091 无 arm64，说明支持是近期才补齐的可用
前端构建node:20-slim 有 arm64 版本，vite/esbuild 有 arm64 二进制可用
结论：arm64 镜像可以构建，Dockerfile 几乎不用改。主要成本在验证而非改造：需要一台 arm64 构建机（或 buildx + QEMU，但 QEMU 模拟构建极慢，前端 vite 阶段容易 OOM，建议用真机）。工作量估算 1–2 人日。

5. 鲲鹏与昇腾要分开看 容易被混为一谈

鲲鹏（Kunpeng 920）昇腾（Ascend NPU）
性质ARM64 CPUNPU 加速卡
与 Octop 容器的关系强耦合。容器共享宿主内核，容器内进程直接跑在宿主 CPU 上，镜像内所有二进制必须是 aarch64零耦合。Octop 代码里没有任何 CANN/Ascend 集成，模型接入走 OpenAI 兼容 HTTP
需要做什么构建 arm64 镜像Octop 侧什么都不用做
宿主依赖仅需 Docker/容器运行时支持 aarch64宿主装 HDK（driver + firmware）、装 Ascend Docker Runtime、容器加 --runtime=ascend 并挂载 /dev/davinci*、/dev/davinci_manager、/dev/hisi_hdc、/dev/devmm_svm、/usr/local/Ascend/driver——这些全部属于推理服务容器，不属于 Octop
交付口径：昇腾 NPU 的算力属于推理平台交付项，不属于 Octop 交付项。正确形态是两个容器：Octop（CPU，普通容器，无需特权）+ 推理服务（MindIE / vLLM-Ascend，需 NPU 直通）。不要为了省事把两者塞进同一个容器——那会把 CANN 版本与内核的强绑定风险带进应用层，升级一次模型就要动 Octop。
还需向客户澄清的三件事（直接影响报价）：
① 客户要的是鲲鹏 CPU 信创（国产化替代）还是昇腾 NPU 推理（本地大模型），还是两者都要？三者工作量差一个量级。
② 宿主操作系统是什么？如果是 openEuler，默认容器引擎可能是 iSulad（华为自研）而非 Docker，docker compose 方案不通用，需改造成本 2–3 人日。
③ 昇腾的 HDK/CANN 与内核、固件三者版本强绑定，谁负责这台机器的驱动运维？这是长期成本，不是一次性交付。

落地建议 可直接执行

推荐形态：官方镜像 + 单副本 + 外置 PostgreSQL(pgvector) + 非 root 运行 + 前置 nginx。所需文件已生成在 octop-deploy/ 目录（Dockerfile、root 入口脚本、compose、env 模板）。 
# 1) 拉取官方镜像（有网机器）
docker pull ghcr.io/tencentcloud/octop:1.0.0

# 2) 叠加加固层（补 Chromium + 非 root + 修 P0 初始化判据）
cd octop-deploy && docker build -t octop-hospital:1.0.0 .

# 3) 离线导出 / 内网导入
docker save octop-hospital:1.0.0 pgvector/pgvector:pg16 | gzip > octop-offline.tar.gz
# 内网： gunzip -c octop-offline.tar.gz | docker load

# 4) 宿主准备（非 root 运行的前置条件）
sudo mkdir -p /srv/octop/data && sudo chown -R 10001:10001 /srv/octop/data

# 5) 起服务
cp .env.example .env   # 填 OCTOP_DATA / POSTGRES_PASSWORD / OCTOP_DEFAULT_PASSWORD
docker compose up -d
已生成的交付件：octop-deploy/ 目录（Dockerfile 加固层、修好初始化判据的入口脚本、compose、pgvector 初始化 SQL、env 模板、说明文档）。入口脚本语法与 compose 配置已校验通过；镜像构建与容器启动尚未实测（本机 Docker daemon 未运行）。

LLM 走内网

把 Provider 配成 OpenAI 兼容端点指向院内推理服务（如已调研的昇腾 + DeepSeek-V4-Flash），或直接用 Ollama 预设。这样数据不出院内网，是医院项目能过审的前提。

要提前说清的交付边界

  • 无高可用：单副本，故障即中断，恢复依赖容器重启 + 数据卷完整。若客户要求 HA，需要额外 3–5 人日做双活改造（且改造点在上游 harness 栈，非本项目可控）。
  • 无 arm64 官方镜像：依赖树已实测无阻塞，主要是构建与验证成本，1–2 人日；若宿主是 openEuler + iSulad 再加 2–3 人日。
  • 无商业支持：MIT 开源，问题响应靠社区。医院 3–5 年维保要求需商务侧先确认。
  • 上游依赖未开源：harness-agent / harness-gateway / harness-memory / harness-browser 官方称"正在准备开源"，仓库链接待发布。目前只能通过 PyPI 包使用，遇到深层问题无法自行定位到源码——这是最大的技术风险。
  • P0 缺陷需自行背补丁：PG 初始化判据的修复在上游合入前由本项目维护。每次升级官方镜像都要重打一次加固层，属长期维护成本，建议记入运维人日。
