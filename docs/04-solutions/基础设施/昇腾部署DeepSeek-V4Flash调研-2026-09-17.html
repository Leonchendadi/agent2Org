结论先行

V4-Flash 单机就能跑，32G 卡也行
1 台 Atlas 800 A2 即可。64G 卡走 W8A8，32G 卡（910B4×8）实测也能跑，但必须降到 W4A8——这是目前昇腾侧门槛最低的 V4 系路径。代价是精度有损，且官方文档里没写这条路。
V4.1-Flash 门槛是 V4-Flash 的 4 倍
需要 2 台 Atlas 800 A3（128G×8）或 4 台 A2（64G×8）。且官方文档明确写着"生产性能认证与任务级精度评估尚未完成"，现阶段不宜直接进生产。
没有 MindIE 路径
两个模型在昇腾上都只走 vLLM-Ascend。MindIE 官方模型列表里没有 V4 系列。且文档迭代极快（V4.1 教程 1 天前刚更新），任何一次跑通的参数都不能当成永久兼容矩阵。
术语更正：昇腾不是 GPU，是 NPU（达芬奇架构）。本文涉及设备为 Atlas 800 A2 / A3 训练推理服务器，卡型对应 910B 系列。网上大量"昇腾 GPU 部署"的说法是错的，选型文档里不要沿用，容易被客户技术方挑。

四、启动命令

V4-Flash · 单机 A2（DP1 / TP8）

# 镜像：quay.io/ascend/vllm-ascend:v0.26.0rc1
vllm serve /root/.cache/modelscope/hub/models/vllm-ascend/DeepSeek-V4-Flash-w8a8-mtp \
    --max-model-len 133120 \
    --max-num-batched-tokens 8192 \
    --served-model-name dsv4 \
    --gpu-memory-utilization 0.9 \
    --max-num-seqs 32 \
    --data-parallel-size 1 \
    --tensor-parallel-size 8 \
    --enable-expert-parallel \
    --tokenizer-mode deepseek_v4 \
    --tool-call-parser deepseek_v4 \
    --enable-auto-tool-choice \
    --reasoning-parser deepseek_v4 \
    --quantization ascend \
    --block-size 128 \
    --speculative-config '{"num_speculative_tokens":1,"method":"mtp","enforce_eager":true}' \
    --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}' \
    --port 8900

要点：--tokenizer-mode / --tool-call-parser / --reasoning-parser 三件套必须显式指定为 deepseek_v4，否则工具调用与思考链会解析失败。DSpark 场景把 method 换成 dspark，且 num_speculative_tokens 必须 ≥ 5。

V4.1-Flash · A2 双机（每节点 DP1，全局 DP2 / TP8 / EP）

五、裸机安装路径（Conda，无 Docker） 官方文档没写

为什么需要这条路：官方文档只给 Docker 镜像。但社区实测走通了 Conda 裸机安装，适用场景是——现场不允许 Docker、需要精确锁定 CANN 版本、或者用的是 32G 卡只能吃 W4A8 的配置。
代价：没有任何厂商兜底，环境全靠自己维护，且下面这些版本号是一次实测成功的组合，不是兼容矩阵。

安装步骤

# 1. 建环境
conda create dsv4-flash python=3.12 -y
conda activate dsv4-flash
conda config --add channels https://repo.huaweicloud.com/ascend/repos/conda/

# 2. 装 CANN（三个包，顺序不能乱）
conda install ascend::cann-toolkit==9.0.1 -y
conda install ascend::cann-910b-ops==9.0.1 -y    # 按机器系列选，910b 用这个
source $CONDA_PREFIX/Ascend/cann/set_env.sh       # 不激活则 NNAL 装不上
conda install ascend::cann-nnal==9.0.1 -y
source $CONDA_PREFIX/Ascend/nnal/atb/set_env.sh

# 3. 装推理框架
pip install vllm==0.22.1
pip install vllm-ascend==0.22.1rc1 --extra-index-url https://mirrors.huaweicloud.com/ascend/repos/pypi
两个坑：① 官方教程里写的 pip 源地址是错的（末尾多了一个 /variant），用上面这个不带 variant 的；② 两次 source set_env.sh 不是永久的，每次进 conda 环境都要重新执行，建议写成脚本或塞进 activate.d。若报 torch_npu 相关安装错误，八成是忘了激活环境。

六、官方明确写出的限制 别自己猜

模型限制
V4.1-Flash
  • 不支持 PD 分离（Prefill-Decode 分离），文档原文明确"not covered by this guide"
  • 不支持流水线并行、不支持 model runner V2、不支持 Engram host offloading
  • DSpark 的 num_speculative_tokens 必须 ≥ 5，Prefill 与 Decode 两侧投机 token 数必须一致
  • DSpark draft 以 eager 模式运行，目标模型用 FULL_DECODE_ONLY ACL Graph
  • 生产性能认证与任务级精度评估尚未完成，官方未发布该配置的性能基线
  • 精度 / 性能验证需自行按 AISBench 跑，报告要记录 checkpoint、prompt encoder、reasoning effort、采样参数、是否启用 DSpark
V4-Flash
  • DSpark 的 num_speculative_tokens 必须 ≥ 5（需核对 checkpoint 的 config.json）
  • DeepSeek-V4 KV Pool 部署必须加 --no-disable-hybrid-kv-cache-manager，否则启动过程中可能 OOM
  • 不要在同一 MoE 层混用 MoE 张量并行与专家并行
  • enable_dsa_cp 依赖 FlashComm1，两者必须同时显式启用
  • recompute_scheduler_enable 只在 PD 分离的 decode 节点上开
  • MTP 建议 Prefill 设 1，Decode 设实际投机 token 数

七、实战坑 踩过的

上半部分来自 16×910B2C 部署复盘，下半部分来自 8×910B4 32G 部署复盘。均为单环境实测结论，不可直接外推。

现象原因与处置
/health 返回 200，但请求 120 秒不出 token 健康接口只证明 API 进程活着，引擎可能卡在图 / 算子 / 通信步骤。必须同时看 metrics：vllm:num_requests_running 长时间不变、generation_tokens_total 不增长，就按"生成停滞"处理，不要继续等健康检查变红
大批处理量下卡死 16 卡 910B2C 实测：--max-num-batched-tokens 从 16384 降到 8192 后，普通 API、基准请求、Agent 多轮工具循环全部稳定。属该环境实测结论，不要外推成"所有昇腾只能用 8192"
换镜像后 512K 上下文装不下 上下文能力 = 权重 × 镜像 × 缓存实现 × 并行方式的组合结果，不能只看标称 HBM。必须用与权重配套的专用镜像
16 卡比 8 卡还慢 不要硬凑 TP16。跨 8 卡 HCCS 域会走到 PIX/PHB/SYS，集合通信延迟反而上升。正确做法是固定 TP8/DP1 在一个高速互联域内，另 8 卡给第二个服务
Agent 调用一次工具后"不说话" 客户端未设输出上限时会把 max_tokens 放大到接近整个上下文（50 万量级）。服务端加 --override-generation-config '{"max_new_tokens":65536}' 兜住
首请求特别慢 首次 ACL Graph 回放实测约 19 秒。压测必须包含预热阶段，否则数据没意义
容器 running 但重启数百次 先 docker inspect 看 RestartCount / 实际 Cmd / 挂载，不要直接重启。一次中断的下载会留下 .incomplete 和重复分片，"目录很大"不等于权重完整
性能参考区间
16×910B2C		 TP8 DP1 / 512K 上下文 / DSpark 5 token：活跃生成吞吐约 35–55 token/s，短窗口峰值 70–82 token/s，DSpark 接受率 20%–60%。属单环境实测，不是厂商承诺
Prefill 是短板
8×910B4 32G		 1 个 token 的 TTFT 就要 600ms；装 6k token 时 TTFT 恶化到 6000ms。部分原因是分块预填充只开到 2048（开大极大影响显存）。长输入场景要单独压测，不能拿短请求的 TTFT 去承诺客户
--max-model-len 的真实语义 它只影响 vLLM 的计算，不等于"给每个请求预留了这么多 KV"。高并发下长上下文仍会互相抢占显存，对各项指标影响极大。没有极致上下文需求就开到 128K 往下——作者原话是"最好的还是力大砖飞把上下文长度削了"
投机采样只能用 MTP DSpark 官方明确说发行版本用不了；作者自己编译 Nightly 版也有问题，正在给源仓库提 issue。MTP 的投机 token 数官方建议为 1，多了命中率和推理速度都会迅速恶化
LMCache-Ascend 官方配置严重过时 照官方文档配会产生"内存页算出来过大"的报错，新配置用不上。要用 LMCache 得自己改
CPU 模型权重卸载不可用 该模型不支持 CPU offload，别指望靠卸载省显存
并发与单序列速度的取舍 32G 卡实测：64 并发吞吐可拉到近 1k token/s，但每个并发都很慢。要单序列快就减并发，要吞吐就加并发，没有两头都占的配置
并行策略的直觉修正 DP 是复制权重、不省显存，只提吞吐；EP 只对 MoE 模型有用；TP 多卡环境必用。PD 分离同样要复制权重。DSA-CP 占显存高出一大截，得用层分片压，而层分片只适用于 PD 分离的 P 节点
