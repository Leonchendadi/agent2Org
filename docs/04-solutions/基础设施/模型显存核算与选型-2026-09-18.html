结论 不够

200GB 不够跑 V4，差 2.5–10 倍
V4-Flash W8A8 需 512GB（8×64G）；V4.1-Flash 需 2048GB（2×A3 或 4×A2）。200GB 无论哪条路都进不去。
"开 FP8 精度"这个选项在昇腾上不存在
昇腾 910B 不支持 FP8 格式。V4.1-Flash 原生 FP8/FP4 权重（约 511GB）到昇腾侧必须转成 W8A8（INT8）或 BF16。这不是显存够不够的问题，是硬件能力问题。
1M 上下文只有 V4.1-Flash 支持
V4-Flash 稳定基线 256K，官方启动配置 --max-model-len 133120。而 V4.1-Flash 官方文档写明"生产性能认证与任务级精度评估尚未完成，现阶段不宜直接进生产"。
但 20 人根本不需要 V4
20 名医护的 RAG 问答，峰值并发个位数。32B 级模型（Qwen3-32B 等）足够，200GB 绰绰有余，还能留出冗余。
一句话：你问的"200GB 够不够开 FP8 + 1M 上下文"，前提有两处不成立——昇腾开不了 FP8，V4 系列里只有 V4.1-Flash 支持 1M 而它要 2048GB。但好消息是：20 人的场景用 32B 级模型就能覆盖，200GB 不是不够，是买错了方向——把钱花在了远超需求的模型规格上。

三个硬事实 已核实

事实核实结果来源
昇腾 910B 不支持 FP8 910B 只支持 FP16 / BF16 / INT8。DeepSeek 官方发布的 FP8 权重在昇腾上必须转换格式才能加载——R1 时代就是这个情况（FP8 权重约 640G，转 BF16 后翻倍）。V4 系列同理，昇腾侧走的是 W8A8（INT8）量化路径 多来源一致（CSDN / 知乎昇腾部署复盘）
V4 系列最小尺寸是 552B DeepSeek V4.1-Flash 是"全新模型结构系列中最小尺寸的成员"，主干 552B、总参约 769B、激活 16B。V4 系列没有 32B 级别的小模型 官方发布信息（2026-09-10）
V4 系在昇腾上只走 vLLM-Ascend MindIE 官方模型列表里没有 V4 系列。且官方只验证了 Atlas 800 A2 / A3 两种机型；Atlas 800I A2 与 Atlas 300I Duo 在 V4 系文档中完全未被提及 vLLM-Ascend 官方教程
你的调研文档（2026-09-17）已经把这些摸清了，本次核算沿用其中的权重规模数据，并补充了"FP8 在昇腾不可用"与"卡型支持范围"两条边界。

四类模型的显存分配 关键建议

先纠正一个前提：WeKnora 本身不吃显存。它是纯编排层——文档解析、分块、检索编排、Agent 调度，模型全部通过 OpenAI 兼容 API 外部调用。所以 200GB 可以全部给模型服务，不需要给 WeKnora 留一份。

模型类型推荐选型显存部署位置建议
LLM 见下一节选型 大头 NPU（vLLM-Ascend）
Embedding BGE-M3（1024 维，中文医学语料表现好） ≈ 2.3 GB 建议 CPU 20 人并发下 CPU 延迟可接受，不占显存
Reranker bge-reranker-v2-m3 ≈ 2.3 GB 建议 CPU 同上，调用量比 embedding 更低
ASR Qwen3-ASR-1.7B（昇腾已有适配案例）
或 Paraformer / Whisper		 ≈ 3.5 GB 建议 NPU ASR 在 CPU 上实时率差，且调用频次低，占显存极小
三类小模型合计 ≈ 8 GB 相对 LLM 可忽略，但能放 CPU 就放 CPU
结论：Embedding 与 Reranker 放 CPU 跑，ASR 放 NPU（占 3.5GB）。200GB 里可以拿出约 190GB 给 LLM。

KV cache 按 GQA 架构估算（32B 级：64 层 × 8 KV heads × 128 dim × 2 × 2 bytes ≈ 256 KB/token）。DeepSeek 系列用 MLA 架构，KV 显著更小，但权重本身就是瓶颈。

20 人的真实负载：20 人 × 每天 30 次提问 ≈ 600 次/天，折算峰值并发个位数。RAG 场景每次检索回来的上下文通常 4K–16K token。32B 级模型在这类负载下毫无压力——用 V4 是 10–20 倍的过度配置。

1M 上下文与 RAG 的关系 需求本身要打个问号

这一条值得单独说：1M 上下文和 RAG 在技术上是相互替代的关系，不是叠加关系。

1M 长上下文RAG 检索增强
思路把全部资料塞进上下文，让模型自己找先精准检索出相关片段，只把片段给模型
成本KV cache 随长度线性增长，显存与延迟都爆炸KV cache 稳定在 8K–32K，成本可控
准确率长上下文中间部分易被忽略（lost in the middle）召回质量取决于检索，但可优化、可评测
医院场景适用性适合"通读一份长病历"这类任务适合知识库问答，这是主场景
判断：你要建 RAG 知识库，那么 1M 上下文基本用不上——RAG 的价值恰恰在于不需要把全部资料塞进上下文。1M 是模型厂的营销参数，不是医院知识库的必需能力。为了一个用不上的能力去补 10 倍硬件（200GB → 2048GB），是这次选型里最大的浪费点。

WeKnora 部署要点 已核实源码

项目情况
资源占用不吃显存。已核对 docker-compose.yml 全文，零 GPU 配置（无 runtime: nvidia、无 deploy.resources 设备段）。纯编排层
服务组成多容器栈，不是单体。基础部署 6 个容器：frontend（Vue）/ app（Go 后端）/ docreader（文档解析）/ postgres / redis / mcp。另有可选 profile：searxng、minio、neo4j、qdrant、milvus、weaviate、doris、dex、langfuse
部署方式Docker Compose（profiles：core / full / neo4j / minio / langfuse），也支持 K8s Helm。官方支持私有化与离线部署
数据库
重要修正		 用的是 ParadeDB（镜像 paradedb/paradedb:v0.22.6-pg17），不是普通 PostgreSQL——这是 PG 17 + pg_search + pgvector 的扩展发行版，同时承担主库（DB_DRIVER=postgres）和向量存储（RETRIEVE_DRIVER=postgres）两个角色。
与 Octop 侧用的 pgvector/pgvector:pg16 版本与扩展均不同，技术上无法共用实例——不是"建议分开"，是硬约束。两台服务器各自独立部署
模型接入5 种模型类型：KnowledgeQA（LLM）/ Embedding / Rerank / VLM / ASR。全部为 source: remote 的 API 调用（base_url + api_key）
模型配置方式两条路径：① .env 环境变量（LLM_* / EMBEDDING_* / RERANK_*，模板 788 行，中文注释）；② 声明式 config/builtin_models.yaml（启动时 upsert 入库）。ASR 没有环境变量模板，需走 YAML 或前端模型管理界面配置
Reranker 选型官方 BUILTIN_MODELS.md 示例用的就是 bge-reranker-v2-m3——与本文档推荐一致，可直接照抄
与 Octop 的集成官方提供 MCP Server（PyPI tencent-weknora-mcp，29 个工具，支持 stdio / SSE / HTTP）。Octop 原生支持 MCP → 两者通过 MCP 对接，不需要改任何一方代码
集成架构很干净：Octop（Agent 平台，MCP 客户端）→ MCP → WeKnora（RAG 编排）→ OpenAI 兼容 API → 院内 vLLM-Ascend 模型服务。三层解耦，任一层替换不影响其他两层。
资源规划提醒：WeKnora 是 6 个容器的微服务栈，加上 Octop 侧的 3 个容器（Octop + PG + nginx），联想服务器上实际要跑 9 个左右容器。原来给 Octop 估的 4C8G 需要重算——建议单独出一份资源核算，把这套栈的 CPU / 内存 / 磁盘需求列清楚。官方 README 未给出明确的系统配置要求，需按实际知识库规模压测确定。

需澄清项 阻塞选型

编号问题为什么关键
G1 "200GB" 的确切构成是什么？几张卡 × 单卡多少 GB？ 显存不是按 GB 买的，是按卡买的。卡数比容量更致命——昇腾部署 V4 系需要 TP8（8 卡）拓扑，如果只有 3–4 张卡，连并行拓扑都组不起来
G2 卡型是 Atlas 800I A2（8 模组推理服务器）还是 Atlas 300I Duo（推理卡）？ 两者在 vLLM-Ascend 的 V4 系文档中完全未被提及，不在官方验证路径内。若现场是 300I Duo，需单独向华为确认，否则出问题没有官方兜底
G3 甲方是否硬性要求"必须部署 DeepSeek V4"？还是只要求"本地大模型"？ 这一条决定路径 A / B / C。如果只是要求本地化，32B 级模型完全达标，能省下 2.5–10 倍硬件预算
G4 1M 上下文是真实业务需求还是看参数表选的？ RAG 场景用不上 1M。若确有"通读长病历"类需求，需单独评估，而不是为它上 2048GB
G5 ASR 的使用场景是什么？（语音录入病历？会议记录？） 决定选型：短语音指令用 0.6B 级即可；长音频转写需更大模型与更长显存占用
G6 知识库规模有多大？文档数量与类型？ 决定 embedding 与 reranker 的吞吐需求，以及向量库选型
